# Архитектура TaskFlow

## Общая схема

```text
Браузер
   |
   v
FastAPI routes  --->  Pydantic schemas
   |                         |
   v                         v
JWT security             SQLAlchemy models
   |                         |
   +-------------> SQLite / PostgreSQL
```

## Слои приложения

- `web` отвечает за интерфейс и пользовательские действия;
- `api/routes.py` принимает HTTP-запросы и возвращает JSON;
- `schemas.py` проверяет данные до записи в базу;
- `security.py` хеширует пароли, создает JWT и проверяет роли;
- `models.py` описывает таблицы пользователей, клиентов и заказов;
- `database.py` создает подключение SQLAlchemy.

Такое разделение не дает всей логике смешаться в одном файле и облегчает
тестирование отдельных частей.

## Авторизация

Пароль не хранится в открытом виде. При регистрации создается scrypt-хеш с
уникальной солью. При входе пароль хешируется повторно и сравнивается с
сохраненным значением.

После успешного входа сервис возвращает JWT. Клиент передает его так:

```text
Authorization: Bearer <token>
```

В токене хранится идентификатор пользователя, роль и срок действия. Сервер
проверяет подпись токена и загружает актуального пользователя из базы.

## Роли

- `admin` может создавать и изменять данные, а также удалять клиентов и заказы;
- `manager` может работать с клиентами и заказами, но не удалять их.

В реальном продукте роли нужно хранить в отдельной таблице permissions, если
прав становится больше.

## Связи данных

```text
User 1 ---- * Order * ---- 1 Client
```

Один пользователь может создать много заказов. Один клиент может иметь много
заказов. При удалении клиента его заказы удаляются каскадно.

## Дальнейшее развитие

Для production-версии стоит добавить миграции Alembic, PostgreSQL, пагинацию,
refresh-токены, аудит изменений, историю статусов и фоновые уведомления.
